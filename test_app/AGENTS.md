# RideSync Android App - AGENTS.md

## 1. 프로젝트와 적용 범위

RideSync는 자전거 그룹 라이딩을 지원하는 Android 애플리케이션이다.
앱은 사용자 인증, 그룹 관리, 라이딩 초대와 참여, 실시간 신호, 주행 종료 및 개인 주행 기록 기능을 제공한다.
각 기능의 구현 여부는 실제 코드와 서버 명세를 확인한다.

- 이 지침은 test_app/ 및 그 하위 작업에 적용한다.
- 기존 코드, README.md, 빌드 설정과 관련 문서를 먼저 읽는다.
- server/의 코드, 설정, DB 구조는 별도 요청 없이 변경하지 않는다.
- 백엔드 변경이 필요하면 사유와 영향을 설명하고 승인을 받는다.

## 2. 기술 스택과 아키텍처

- Kotlin, Jetpack Compose, Material 3를 사용한다.
- 기존 단일 app 모듈의 feature-first + MVVM + Repository 구조를 따른다.
- 기본 패키지와 applicationId인 com.example.ridemate_api_test를 임의로 변경하지 않는다.
- app/navigation은 앱 진입과 화면 이동, app/session은 세션 및 앱 공통 상태 조정을 담당한다.
- core/designsystem은 테마와 공통 UI, core의 network/websocket/datastore/location은 공통 기반을 담당한다.
- 기능별 presentation에는 Route, Screen, ViewModel, UiState를 둔다.
- domain에는 모델과 Repository 인터페이스, data에는 API/DTO와 Repository 구현을 둔다.
- Route는 상태 수집과 이벤트 연결을, Screen은 전달받은 상태의 표시와 사용자 이벤트 전달을 담당한다.
- UI에서 직접 네트워크 요청이나 저장소 접근을 하지 않는다. ViewModel은 Repository 인터페이스를 통해 작업한다.
- Compose 재구성으로 요청이나 WebSocket 연결이 반복되지 않도록 한다. 상태 수집은 생명주기를 고려한다.
- 기존 AppContainer 기반 수동 의존성 주입을 우선 사용한다.
- usecase, mapper, local, service 등은 실제 필요할 때 추가한다. 빈 계층이나 불필요한 추상화를 만들지 않는다.
- 기존 코드 스타일을 따르고, 화면마다 같은 API 호출이나 오류 처리 코드를 중복 작성하지 않는다. 공통화는 실제로 필요한 범위에서만 수행한다.
- 서버 응답 모델과 화면 상태를 필요한 범위에서 구분한다. 제품 문구는 문자열 리소스로 관리하고 기존 한국어 표현을 일관되게 사용한다.
- 새로운 라이브러리나 아키텍처 변경은 필요성과 영향을 설명하고 승인받는다.

## 3. 참조 문서

- README.md: 프로젝트 구조와 실행 방법
- ../server/docs/API_SPEC.md: REST API 및 WebSocket 계약
- ../server/docs/DATABASE.md: 데이터 구조 및 관련 비즈니스 규칙

- docs/SIGNUP_DEVELOPMENT_PLAN.md: 회원가입 단계별 결정·구현 결과·남은 통합 검증·작업 재개 지점

API 명세를 앱 문서에 복제해 별도로 관리하지 않고 서버 문서를 참조한다.
문서, 서버 구현, 앱 요구사항이 다르면 차이를 설명하고 확인 후 진행한다.
docs/APP_UI_GUIDELINES.md가 작성되어 있으면 UI 작업 전에 반드시 읽는다.
해당 문서가 아직 없으면 이 파일의 UI 규칙을 적용하며, 미작성 문서를 읽었다고 보고하지 않는다.

## 4. 단계별 개발 방식

1. 요청한 화면이나 기능과 관련된 문서 및 기존 구현을 확인한다.
2. 변경 범위, 구현 순서, UI 상태, 화면 이동, API 연동 및 검증 방법을 한국어로 제시한다.
3. 사용자가 승인한 단계만 구현한다. 이미 명확히 승인한 범위는 재승인받지 않는다.
4. 구현과 검증 결과를 보고하고 다음 단계로 자동 진행하지 않는다.

기존 기능을 재사용하고 요청과 무관한 리팩터링, 디자인 변경이나 기능 추가를 하지 않는다.
별도 요청 없이 커밋, 푸시, 브랜치 변경을 하지 않는다.

작업 중단이나 채팅 이동에 대비해 관련 개발계획 문서에 승인 범위, 완료 지점, 수행한 검증, 남은 문제와 바로 다음 작업을 갱신한다. 기존 기록을 현재 코드의 증거로 단정하지 않고 변경 여부를 확인한다.

## 5. Figma 기반 구현

- 사용자가 제공한 Figma URL의 대상 프레임과 구현 범위를 확인한다.
- 레이아웃, 색상, 글꼴, 간격, 컴포넌트 상태와 이미지 자산을 확인하고 기존 디자인 시스템을 재사용한다.
- Figma 프레임 크기는 디자인 참고값이며 실제 기기의 고정 화면 크기로 사용하지 않는다.
- 절대 좌표를 그대로 옮기지 않고 정렬, 간격, 비율, Auto Layout과 제약 조건의 의도를 해석한다.
- 디자인을 충실히 반영하되 실제 화면에서 콘텐츠 접근성과 조작 가능성을 확보한다.
- Figma에 없는 버튼 동작, 화면 이동, 오류 처리 및 비즈니스 규칙은 서버 명세와 요구사항으로 확인한다.
- 확인할 수 없는 동작을 임의로 확정하지 않는다. 디자인 접근이 불가능하면 그 사실을 알린다.
- 실제 기능과 미리보기용 샘플 데이터를 구분하며, 샘플 성공 결과를 실제 서버 응답처럼 사용하지 않는다.

## 6. 화면 크기와 유연한 레이아웃

- 지원 대상은 Android 휴대폰의 세로 화면이다. 태블릿·가로 화면 전용 설계와 Preview는 기본 작업 범위에서 제외한다.
- 우선 확인 기기는 갤럭시 S26+와 갤럭시 S10 5G이다. 팀원들의 Android 휴대폰은 모델·Android 버전을 확인한 뒤 최종 점검에 포함하며, 제조사와 사양을 추정해 확정하지 않는다.
- 화면별로 하나의 유연한 UI를 구현한다. 기기마다 별도 화면을 만들거나 모든 화면 크기에 대한 대응을 목표로 범위를 확장하지 않는다.
- 화면 전체 너비나 높이를 특정 휴대폰 또는 Figma 프레임 크기로 고정하지 않는다.
- 전체 화면을 일괄 확대·축소하는 방식으로 기기 크기에 맞추지 않는다.
- 물리 해상도 대신 현재 앱 창과 부모 레이아웃에서 사용 가능한 공간을 기준으로 배치한다.
- 치수는 dp, 글자 크기는 sp를 사용한다. 버튼, 아이콘, 여백에는 의미 있는 기준 크기를 사용한다.
- Row, Column, Box 및 적절한 가중치·크기 제약을 사용해 콘텐츠 너비와 남는 공간을 조정한다.
- 휴대폰의 가용 너비에서 콘텐츠가 과도하게 늘어나면 필요한 최대 너비 제한을 적용한다.
- 작은 화면에서 콘텐츠가 높이를 초과하면 스크롤을 제공한다. 목록은 적절한 Lazy 컴포넌트를 사용한다.
- 하단 고정 버튼과 본문이 겹치지 않도록 공간을 확보하고, 스크롤 끝의 콘텐츠도 접근 가능하게 한다.
- 상태 표시줄, 내비게이션 영역과 디스플레이 컷아웃의 인셋을 처리한다.
- Scaffold의 내부 여백과 별도 인셋 처리가 중복되거나 누락되지 않도록 확인한다.
- 키보드가 나타나도 입력란과 주요 동작 버튼에 접근할 수 있도록 IME 인셋과 스크롤을 처리한다.
- 긴 닉네임·그룹명, 여러 줄 문구 및 시스템 글꼴 확대에도 잘림이나 겹침이 없도록 한다.
- 말줄임은 보조 정보 등 적절한 곳에만 사용하고 핵심 정보나 필수 동작을 숨기지 않는다.
- 이미지의 종횡비를 유지하고 용도에 맞게 맞춤 또는 잘라내기 방식을 선택한다.
- 터치 대상은 원칙적으로 최소 48dp를 확보하고, 의미 있는 아이콘에는 접근성 설명을 제공한다.
- 세로 화면 지원 요구사항과 실제 Android 회전 잠금 설정은 구분한다. 문서상의 지원 범위만으로 Manifest나 Activity의 방향 설정을 자동 변경하지 않고, 해당 코드 변경은 승인한 구현 범위에서 처리한다.
- 시연 기기를 우선 검증하되 해당 기기에서만 동작하는 크기 보정을 하지 않는다.

## 7. 서버 연결과 인증

- REST API 기본 주소는 한 곳에서 관리하고 WebSocket 주소도 일관되게 구성한다.
- 서버 IP와 포트를 화면마다 직접 작성하지 않는다. 현재 서버 실행 설정을 확인한다.
- 서버 주소나 포트가 바뀌면 REST와 WebSocket 설정을 함께 확인한다. 현재 프로젝트의 ridesyncBaseUrl·ServerEndpoint 기반 주소 관리를 재사용한다.
- 에뮬레이터, 실제 기기, USB adb reverse 등 연결 방식에 맞는 주소를 사용한다.
- 실제 기기의 localhost는 기기 자신을 가리키므로 USB 포트 전달 여부를 함께 확인한다.
- API 경로, HTTP 메서드, 필드명과 자료형은 서버 명세를 따른다.
- 인증 토큰은 명세에 맞게 전달하고 플랫폼에 적합한 보안 저장 방식을 사용한다.
- 비밀번호, 토큰과 개인 정보를 소스나 로그에 남기지 않는다.
- 인증 만료, 권한 부족, 네트워크 오류를 구분하고 사용자가 이해할 수 있는 문구를 표시한다.
- 로그아웃 시 인증 정보, 사용자 상태 및 관련 연결을 정리한다.
- 서버에서 지원하지 않는 토큰 갱신이나 변경 요청의 무조건 재시도를 임의로 추가하지 않는다.
- 기존 인증 흐름은 관련 코드와 검증 문서를 확인해 유지한다. 회원가입 성공은 로그인 화면 복귀이며 자동 로그인을 추가하지 않는다. 로그인은 JWT 저장과 로그인 WebSocket 연결 완료 후 임시 확인 화면으로 이동하는 흐름이고, 제품 메인 화면 전환은 별도 승인 범위에서 구현한다.

## 8. 화면 상태와 WebSocket

- 로딩, 성공, 빈 결과, 오류 상태를 구분한다.
- 서버 응답을 기다리는 동안 진행 상태를 표시하고, 수행할 수 없는 동작은 버튼 상태와 한국어 안내로 설명한다.
- 중복 클릭과 중복 요청을 방지하고 요청 실패를 성공으로 표시하지 않는다.
- 권한, 초대 만료, 가입 승인·거절과 라이딩 상태는 서버 결과를 기준으로 반영한다.
- WebSocket 경로, 인증, 메시지 형식과 Ping/Pong은 서버 명세를 따른다.
- 연결 소유자와 유지 범위를 명확히 하고 화면 이동 시 불필요한 중복 연결을 방지한다.
- 앱 생명주기, 로그아웃과 라이딩 종료에 맞게 연결·구독·상태를 관리한다.
- 재연결은 무한한 즉시 반복을 피하고 필요한 최신 상태를 서버에서 다시 확인한다.
- 알 수 없거나 잘못된 메시지로 앱이 종료되지 않도록 처리한다.
- 테스트 전용 UI와 일반 사용자 기능은 구분한다.

## 9. 검증과 보고

변경 범위에 맞게 빌드, 정적 분석 및 필요한 테스트를 수행한다.
문서만 변경한 경우에는 앱 빌드를 불필요하게 실행하지 않고 문서 내용과 참조를 확인한다.

화면당 기본 Compose Preview 1개를 원칙으로 한다. 추가 Preview·기기 조건·상태별 캡처는 변경 내용이나 발견한 문제를 검증하는 데 필요한 경우에만 추가한다. 기존의 여러 Preview와 과거 검증 기록을 이후 모든 화면의 필수 기준으로 취급하지 않는다.

UI 변경 시 기본 Preview와 변경 범위에 맞는 빌드·정적 분석을 확인하고, 다음 중 관련 항목만 추가 점검한다.

- Figma와의 시각적 일치 및 실제 조작 흐름
- S26+·S10 5G 중심의 세로 화면 배치와 주요 조작 흐름
- 레이아웃·텍스트 변경 시 필요한 좁은 휴대폰 화면, 확대 글꼴, 긴 텍스트, 빈 데이터·오류 상태
- 입력 폼·인셋 변경 시 키보드 표시 상태와 시스템 상·하단 영역
- 통신 기능 변경 시 REST API 연동, WebSocket 수신·종료·재연결 및 네트워크 단절 시 동작

이미 확인한 문서·디자인·검증 결과는 변경 여부와 현재 작업의 관련성을 판단해 재사용한다. 단순 수정마다 전체 문서·디자인을 다시 조회하거나 모든 조건의 빌드·캡처·UI 자동화를 반복하지 않는다. 새 변경, 실패 또는 미해결 문제가 있을 때 필요한 검증만 반복한다.

Compose Preview 검증과 에뮬레이터·실기기 실행 검증을 구분한다.
검증한 기기, 화면 조건과 결과를 기록하고 실행하지 못한 항목은 이유와 함께 명시한다.
로컬 통신 성공을 외부 네트워크 검증으로, 빌드 성공을 화면 검증 완료로 표현하지 않는다.

작업 결과는 한국어로 작성하고 변경 기능, 주요 파일, 검증 결과, 남은 문제를 간단히 보고한다.
앱 문서와 구현이 달라졌다면 승인된 작업 범위에 해당하는 관련 문서를 갱신한다.
