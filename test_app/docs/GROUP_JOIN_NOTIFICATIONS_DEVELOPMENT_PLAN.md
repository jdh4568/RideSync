# 그룹 가입 신청 알림 팝업 개발계획

작성일: 2026-11-17

## 1. 승인 범위와 현재 상태

- 사용자 요청: 메인 우측 상단 알림 버튼에서 Figma 기반 가입 신청 알림 팝업을 연다. 해당 그룹장만 자신의 그룹 신청을 확인하고 수락·거절할 수 있어야 한다.
- 2026-11-17 사용자 “0단계 진행해줘.”, “1단계 개발 진행해줘.”, “2단계 진행해줘,”에 이어 “3단계 진행해줘,”로 자체 점검·인수인계를 승인했다. **현재 3단계 가능한 자체 점검·인수인계를 완료했다. 실제 Spring 서버는 연결 시간 초과로 미검증이며 실기기는 사용자 후속 확인이다.**
- 승인 단계의 결과·검증 경계는 7절에 기록한다. 범위 밖 기능으로 자동 진행하지 않는다.
- 알림이 없으면 팝업 본문 중앙에 ‘알림이 없습니다.’를 표시한다. 바깥 영역 터치·시스템 뒤로 가기로 팝업을 닫는다.
- 빨간 알림 표시등, 알림용 WebSocket·푸시·백그라운드 조회·주기적 폴링, 처리 완료 알림 보관은 범위 밖이다.
- 기존 인증·세션·재연결·로그아웃·그룹 관리 동작을 유지한다. 서버 코드·설정·DB, 새 라이브러리, 무관한 리팩터링·디자인 변경, 커밋·푸시·브랜치 변경은 허용 범위가 아니다.

- 그룹 관리 API·오류 모델·보호 REST 인증 연결은 구현되어 있다. 가입 신청 목록·승인/거절 메서드는 앱에 아직 없다.
- 서버는 JWT 기준으로 소유 그룹과 신청을 확인한다. 앱에서 다른 그룹장의 신청을 받아 필터링하는 방식으로 구현하지 않는다.

## 3. Figma와 API 대응

| UI 동작 | 서버 명세 참조 |
|---|---|
| 그룹장이 소유한 그룹들의 대기 신청 조회 | 12.1 GET /api/v1/groups/join-requests |
| 수락 | 12.2 POST /api/v1/groups/{groupId}/requests/{userId}/approve |
| 거절 | 12.3 POST /api/v1/groups/{groupId}/requests/{userId}/reject |

API 상세 계약은 서버 명세를 참조하고 이 문서에 별도로 복제해 관리하지 않는다.

확정한 범위와 계약 차이:

- ‘가입 신청 이력’은 **현재 처리할 PENDING 신청 목록**이다. 현재 서버는 승인·거절 완료 이력, 신청 날짜, 읽음 상태를 제공하지 않으므로 이번 화면에 추가하지 않는다.
- 여러 그룹의 그룹장이면 해당 그룹들의 신청을 하나의 목록으로 표시한다. 항목 문구는 ‘닉네임님이 그룹명에 가입을 요청하였습니다.’로 한다.
- 서버 순서를 유지한다. 현재 조회는 멤버 레코드 ID 순서이며 신청 날짜 기준 최신순으로 표현하지 않는다.
- groupMemberId를 항목 식별에 활용하고 실제 처리 API에는 해당 항목의 groupId·userId를 사용한다. 닉네임·그룹명으로 처리 대상을 식별하지 않는다.
- 대기 신청이 없으면 빈 배열을 받는다. 반면 소유 그룹이 없는 사용자는 현재 목록 API에서 403을 받는다.
- 이 조회 API의 소유 그룹 없음/비그룹장 403은 성공한 빈 배열과 다른 권한 상태로 관리한다. 화면 중앙에 ‘알림이 없습니다.’와 ‘그룹장인 그룹의 가입 신청만 확인할 수 있습니다.’를 함께 안내한다. 처리 API의 403은 권한 오류로 표시한다. 401·네트워크·서버 오류를 빈 목록으로 바꾸지 않는다.
- 수락·거절 성공 응답을 검증한 뒤 해당 항목을 제거한다. 거절 후 사용자가 재신청하면 새 PENDING 신청이 다시 표시될 수 있으므로 처리한 레코드 ID를 영구 차단하지 않는다.
- 서버 승인 시 정원을 검사하며, 정원 도달은 GROUP_FULL 충돌이다. 이 경우 요청을 성공 처리하거나 알림을 지우지 않는다.

## 4. 팝업·상태·요청 처리

### 열기와 조회

- 메인 위에 어두운 배경과 흰색 ‘알림 내역’ 팝업을 표시한다. 다른 페이지로 이동하거나 기존 메인을 새로 만들지 않는다.
- 팝업을 열 때 최신 목록을 한 번 조회한다. Compose 재구성·알림 버튼 연속 클릭으로 중복 요청·중첩 팝업이 생기지 않게 한다.
- 열린 상태의 실시간 신규 신청 수신은 범위 밖이다. 닫았다 다시 열면 최신 상태를 조회한다.
- 최초 로딩·목록·빈 결과·비그룹장·조회 오류를 구분한다. 실패에는 다시 시도를 제공한다.
- 실제 API 연결 전 1단계에서는 준비 중 안내를 표시한다. 예시 신청과 성공 결과를 실제 서버 목록처럼 표시하지 않는다. 예시는 Preview에 한정한다.

### 수락과 거절

- 처리 중 대상 항목에 진행 상태를 표시하고 추가 승인/거절 요청을 막아 중복 처리와 승인·거절 동시 요청을 방지한다.
- 서버 응답의 대상·결과를 확인한 뒤 항목을 제거하고 최신 목록을 갱신한다. 마지막 항목이 없어져도 팝업을 유지하며 중앙 빈 상태를 표시한다.
- 정원 초과는 항목을 유지하고 이유를 안내한다. 거절은 가능하게 유지한다.
- 이미 처리된 신청/신청 없음은 안내 후 재조회하여 최신 목록을 반영한다. 실패 응답만 보고 임의로 승인·거절 성공을 표시하지 않는다.
- 네트워크 단절·응답 손상 등 결과가 불명확하면 POST를 자동 재전송하지 않는다. 목록 재확인 전 중복 처리를 막고, 목록에서 사라졌다는 이유만으로 자신이 선택한 동작의 성공을 확정하지 않는다.
- 성공 뒤 재조회가 실패하면 처리 성공과 목록 갱신 실패를 구분해 안내한다.

### 닫기와 세션

- 바깥 터치와 시스템 뒤로 가기는 **처리 요청 중에도** 팝업을 닫는다. 배경의 메인 버튼까지 클릭이 전달되어 다른 화면으로 이동하지 않게 한다.
- 닫기는 이미 전송된 승인·거절을 취소하거나 되돌리는 동작이 아니다. ViewModel에서 전송한 처리의 완료 상태를 관리하고, 재열기와 이전 응답이 경합해 중복 요청·오래된 목록 반영이 발생하지 않게 한다.
- 닫힐 때 조회 요청은 정리할 수 있으나 이미 전송한 변경 요청을 단순 닫기만으로 취소된 성공처럼 취급하지 않는다. 처리 중 재열기는 해당 진행 상태를 유지하고 완료 후 필요한 최신 조회를 연결한다.
- 로그아웃·만료·사용자 변경에는 팝업/목록/처리 상태와 작업을 정리하고 이전 세션의 늦은 응답을 차단한다.
- 기존 AuthenticatedSession·JWT 401 정리 경로를 재사용한다. 새 로그인 요청·토큰 갱신·WebSocket 연결을 생성하지 않는다.

### 유연한 UI

- Figma의 390×844 프레임과 321×590 팝업은 참고값이다. 실제 팝업은 가용 너비·높이와 시스템 인셋을 사용한다.
- 본문은 LazyColumn으로 스크롤하고 안정적인 항목 식별자를 사용한다. 긴 그룹명·닉네임·오류 문구를 줄바꿈하고 버튼에 가리지 않게 한다.
- Figma의 작은 수락/거절 버튼은 시각적 인상을 유지하면서 최소 48dp 터치 영역을 확보한다. 좁은 공간·큰 글꼴에는 필요한 줄바꿈을 허용한다.
- 빈 상태 안내는 별도 팝업을 추가하지 않고 같은 알림 팝업 본문 중앙에 표시한다.

## 5. 구현 구조와 단계별 완료 기준

새 범용 알림 시스템 대신 그룹 기능에 둔다. 기존 feature-first MVVM·Repository·AppContainer를 유지하며 다음 파일을 중심으로 변경한다.

- feature/group/presentation/requests: GroupJoinRequestsRoute·Dialog·ViewModel·UiState.
- feature/group/domain/model: 신청·처리 결과 모델.
- 기존 GroupApi·GroupRepository·GroupRepositoryImpl: 조회·수락·거절 메서드와 응답 검증.
- HomeRoute·HomeScreen: 기존 알림 준비 중 안내를 새 팝업 연결로 교체. 기존 HomeViewModel의 인증·재연결·로그아웃 책임은 유지한다.
- AppContainer·문자열 리소스·관련 테스트와 문서.

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 0. 계획 문서화 | 이 문서와 기존 그룹 실기기 사용자 보고 기록 | 합의·현재 상태·검증 경계·다음 작업 보존. 앱 코드 변경 없음 |
| 1. 팝업 UI·메인 연결 | 알림 팝업·목록/빈 상태·닫기·메인 이벤트 연결 | 기본 Preview 1개·빌드·lint, 샘플과 실제 상태 구분. API 성공 흉내 없음 |
| 2. API·상태 연결 | 그룹장 목록·수락/거절·항목 제거·오류·중복/늦은 응답 방지 | 관련 자동 테스트와 직접 영향받는 회귀 통과. 기존 인증 연결 재사용 |
| 3. 자체 점검·인수인계 | 필요한 추가 Preview·준비된 실제 서버 확인·사용자 실기기 절차 | 수행 결과와 미검증 범위를 구분하고 재개 지점 기록 |

필요하지 않은 domain/usecase·빈 계층·새 라이브러리·독립적인 네트워크/세션 구조를 추가하지 않는다. 범위 밖 동작이 필요해지면 사유와 영향을 설명한 뒤 합의한다.

## 6. 검증 범위

- UI: 알림 팝업 기본 Compose Preview 1개. 정의와 실제 렌더링 확인을 구분한다. 목록·빈 상태·새 오류 안내는 변경상 필요한 조건만 추가 확인한다.
- 빌드·lint: 변경에 맞춰 :app:assembleDebug :app:lintDebug.
- 자동 테스트: 그룹장 범위/비그룹장 403, 빈 결과·오류, 응답 대상 검증, 성공 후 해당 항목 제거, 실패 시 유지, GROUP_FULL에서 거절 가능, 중복 클릭·닫기/재열기 경합, 로그아웃/사용자 변경 후 늦은 응답 차단.
- 기존 그룹 관리·메인·인증 연결 지점에 직접 영향받는 회귀만 확인한다. 변경·실패 없이 이미 통과한 전체 테스트/Preview/기기 조건을 반복하지 않는다.
- JVM/로컬 가짜 HTTP 서버·실제 Spring 서버·Preview·실기기 결과를 각각 기록한다. 실제 서버가 준비되지 않으면 미실행 사유를 명시한다.
- 실기기는 사용자가 휴대폰 1대에서 주요 흐름을 후속 확인한다. 확대 글꼴·추가 기기·모든 오류 조합을 기본 필수 조건으로 늘리지 않는다.
