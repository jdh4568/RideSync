# 그룹 가입 신청 알림 팝업 실기기 인수인계

작성일: 2026-11-17. 지원 범위는 Android 휴대폰 세로 화면이며 사용자가 휴대폰 1대에서 주요 흐름을 확인한다.
구현·승인·검증 근거는 [알림 개발계획](../../GROUP_JOIN_NOTIFICATIONS_DEVELOPMENT_PLAN.md)을 따른다. API 계약은 [서버 명세 12장](../../../../server/docs/API_SPEC.md)을 참조한다.

## 현재 검증 경계

| 구분 | 확인 결과 |
|---|---|
| JVM·로컬 가짜 HTTP | 2단계 알림 상태 17개·HTTP 계약 11개 및 관련 기존 회귀 통과 기록 재사용. 3단계 새 실행 아님 |
| 빌드·lint | 2단계 최종 빌드 성공·오류 0개·기존 파일 경고 20개 결과 재사용 |
| Preview | 2단계 기본 390×844dp 목록, 비그룹장 빈 안내, 긴 이름·불명확 결과·조회 실패·재확인·비활성 버튼 렌더링 결과 재사용. 기본 샘플 복구 확인 |
| 실제 서버 | 3단계에서 127.0.0.1:18080·192.168.0.5:18080 각각 TCP 연결 2초 시간 초과. 샌드박스 밖에서도 확인. 실제 API 요청·인증·처리 미실행 |
| 실기기·에뮬레이터 | 에이전트 실행 없음. 아래 절차는 사용자 후속 확인용 |

이전 그룹 관리 화면의 사용자 기본 실기기 정상 보고는 알림 팝업의 실기기 검증 결과가 아니다. 당시 기기·OS·세부 실행 항목도 추정하지 않는다.

## 준비

- APK: `app/build/outputs/apk/debug/app-debug.apk` ([파일](../../../app/build/outputs/apk/debug/app-debug.apk)). 2단계 산출물이며 3단계에서 재빌드하지 않았다.
- 현재 `gradle.properties`의 `ridesyncBaseUrl`은 `http://192.168.0.5:18080`이다. 이 APK는 해당 주소의 서버를 준비하고 휴대폰에서 접근할 수 있는 Wi-Fi LAN 경로를 사용한다. PC IP가 달라졌다면 [README 연결 설정](../../../README.md#서버-연결-설정)에 따라 주소를 맞춘 뒤 빌드한다. USB 디버깅만 연결했다고 LAN 주소가 USB 통신으로 바뀌지는 않는다.
- USB 전달을 사용하려면 README에 따라 `127.0.0.1:18080` 주소로 빌드하고 `adb reverse tcp:18080 tcp:18080`을 설정한다. REST·WebSocket은 같은 ServerEndpoint 설정을 사용한다.
- 그룹장 계정과 신청자 계정 2개를 준비한다. 한 휴대폰에서 순서대로 로그인·로그아웃해 준비할 수 있다. 테스트용 그룹은 기존 그룹 관리 UI로 만들거나 이미 준비된 그룹을 사용한다.
- 정원 초과까지 확인하려면 정원이 차기 **전에** 대기 신청 2개를 준비한다. 예를 들어 현재 승인 인원 1명·정원 2명인 그룹에서 두 계정이 먼저 신청하면, 한 명 수락 후 나머지 신청의 정원 오류를 확인할 수 있다. 실제 표시 인원·정원을 보고 준비한다.
- 새 계정 생성·기존 실제 그룹 변경을 이 문서의 에이전트 실행 결과로 간주하지 않는다. 계정 정보·비밀번호·JWT는 검증 기록에 남기지 않는다.

## 휴대폰 1대의 주요 확인 순서

1. **목록과 범위**: 그룹장으로 로그인해 메인 알림 버튼을 누른다. ‘알림 내역’이 메인 위에 하나만 열리고 자신이 그룹장인 그룹의 PENDING 신청과 닉네임·그룹명이 표시되는지 확인한다. 다른 그룹장 데이터가 이미 준비돼 있다면 섞이지 않는지도 확인한다. 신청 날짜·읽음·처리 이력·빨간 점은 표시하지 않는다.
2. **닫기·재열기**: 본문을 터치해도 닫히지 않고, 팝업 밖과 시스템 뒤로 가기로 닫히는지 각각 확인한다. 배경의 그룹 관리·라이딩 시작 버튼까지 터치가 전달되지 않아야 한다. 닫았다 다시 열면 최신 목록을 조회한다. 열린 동안 자동 신규 알림 수신은 제공하지 않는다.
3. **수락·정원 초과**: 첫 신청을 수락한다. 처리 중 중복 수락·거절이 막히고 서버 성공 후 해당 항목이 사라지는지 확인한다. 정원이 찬 상태에서 남은 신청을 수락하면 항목을 유지하고 정원 안내를 표시해야 한다. 거절은 계속 가능해야 한다.
4. **거절·마지막 항목**: 남은 신청을 거절한다. 성공 후 항목이 제거되고 마지막 항목이 없어도 팝업이 유지되며 중앙에 ‘알림이 없습니다.’가 표시되는지 확인한다. 거절한 사용자가 다시 신청한 뒤 재열면 다시 처리할 수 있어야 한다.
5. **처리 중 닫기**: 대기 신청을 다시 준비해 처리 직후 바깥 터치/뒤로 가기로 닫고 즉시 재연다. 처리 중이면 진행 상태를 유지하며 중복 요청이 막혀야 한다. 닫기는 이미 보낸 수락·거절의 취소가 아니다. 빠른 서버 응답으로 처리 중 닫기를 재현하지 못하면 미확인으로 기록한다.
6. **비그룹장**: 팝업을 닫고 로그아웃한 뒤 소유 그룹이 없는 계정으로 로그인한다. 알림을 열면 ‘알림이 없습니다.’와 그룹장만 가입 신청을 확인할 수 있다는 안내가 함께 표시되어야 한다. 이전 계정의 신청·처리 메시지가 남지 않아야 한다.

긴 신청자 이름·그룹명이 이미 준비돼 있다면 줄바꿈과 버튼 접근성을 함께 확인한다. 목록이 길면 끝까지 스크롤해 마지막 항목에 접근할 수 있어야 한다. 추가 기기·확대 글꼴 전체 조합을 필수로 반복하지 않는다.

## 관련 조건을 만들 수 있을 때만 추가 확인

- **조회 통신 실패**: 통신을 끊고 알림을 연다. 빈 목록으로 바뀌지 않고 오류·목록 다시 확인이 표시되어야 한다. 복구 후 재확인한다. 로그인 WebSocket 연결이 끊겨도 기존 메인 세션 정책을 유지한다.
- **결과 불명확·갱신 실패**: 처리 응답 시점의 단절을 재현할 수 있다면 변경 요청 자동 재전송이 없고 최신 목록 확인 전 추가 처리가 막히는지 확인한다. 목록에서 사라졌다는 사실만으로 자신이 선택한 처리의 성공을 표시하면 안 된다. 성공 응답은 받았지만 후속 GET만 실패했다면 처리 성공과 목록 갱신 실패를 따로 안내해야 한다. 타이밍이 재현되지 않으면 자동 테스트 근거와 구분해 미확인으로 기록한다.
- **권한·상태 변경**: 처리 API 403은 권한 오류, 이미 처리된 신청/404·409는 안내 후 재조회여야 한다. 목록 조회의 비그룹장 403과 혼동하지 않는다. 재현용 계정·상태가 없으면 강제로 서버/DB를 바꾸지 않는다.
- **만료·로그아웃**: 실행 중 실제 401·만료를 확인할 수 있으면 기존 로그인 복귀와 팝업·이전 사용자 데이터 정리를 확인한다. 자연 만료를 기다리거나 토큰·서버 설정을 임의로 변경하는 작업은 기본 필수 절차가 아니다.

## 결과 전달

기기 모델·Android 버전, 실제 사용한 서버 주소/연결 방식, 위 주요 순서의 통과/실패/미확인과 실패 지점을 알려주면 된다. 표시·터치 문제가 있을 때만 글꼴 크기·내비게이션 방식 등 재현에 필요한 조건을 덧붙인다. 민감 정보 없는 화면 캡처가 있으면 문제 파악에 도움이 된다.

바로 다음 작업은 사용자 실기기 결과를 개발계획에 반영하거나, 준비된 서버에서 아직 실행하지 못한 알림 통합 동작을 확인하는 것이다.
