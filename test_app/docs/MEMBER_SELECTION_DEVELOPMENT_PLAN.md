# 라이딩 멤버 선택 화면 개발계획

## 1. 승인 범위와 현재 상태

- 기준일: 2026-11-18.
- 사용자는 이 채팅에서 제시한 권장 선택·갱신·상태 유지 정책을 승인했다. 아래 정책은 합의 사항이다.
- 사용자는 0단계 완료 후 1단계 UI·화면 이동, 2단계 API·상태 연결, 이어서 **3단계 자체 점검·인수인계 실행까지 순차 승인**했다. 초대 등 후속 기능으로 자동 진행하지 않는다.
- 0단계: 완료. 이 문서 작성, 그룹 선택 계획의 후속 연결·이탈 정책 변경 예정 명시, 문서 내용·참조 확인을 수행했다.
- 1단계 UI·화면 이동: 구현·가능한 자체 검증 완료. 아래 1단계 기록을 따른다. 기기 조작 검증은 미실행이다.
- 2단계 API·상태 연결: 구현·가능한 자체 검증 완료. 실제 서버는 연결 시간 초과로 미검증이다.
- 3단계 자체 점검·인수인계: 완료. 승인 범위·현재 코드·기존 검증 기록을 대조하고 사용자 확인 절차를 정리했다. 실제 서버·실기기 검증 완료를 의미하지 않는다.
- 현재 앱은 그룹 선택 완료 시 실제 그룹 멤버를 조회하고 OWNER·본인을 제외한 목록을 표시한다. 조회 시점 온라인 멤버 1~49명을 선택할 수 있으며 완료는 개발 중 팝업만 표시한다. 예시 멤버는 Preview·테스트에만 있다.

이번 기능의 목표 범위는 **메인 → 그룹 선택 → 멤버 조회·다중 선택 → 선택 완료 → 개발 중 팝업**이다. 팝업을 닫으면 멤버 화면과 선택을 유지한다.
초대 전송·초대 대기 팝업·수락/거절·라이딩 시작·실시간 라이딩은 포함하지 않는다.
서버 코드·설정·DB, 기존 앱 소유 WebSocket의 연결·인증·재연결 정책, 무관한 기능은 변경하지 않는다. 새 라이브러리·빈 계층·불필요한 추상화·무관한 리팩터링·커밋·푸시·브랜치 변경도 범위 밖이다.

## 3. API 적용과 실시간 범위

### 멤버 조회와 대상 판정

- 서버 명세 8.1의 `GET /api/v1/groups/{groupId}/members`를 사용한다. 최상위 배열이 아니라 그룹 메타데이터와 `members`를 포함한 객체를 읽는다.
- 응답에는 그룹장·본인을 포함한 APPROVED 멤버만 있다. PENDING·REJECTED는 조회 대상이 아니다.
- `role == OWNER`인 멤버를 목록에서 제외한다. 현재 로그인 사용자 ID도 초대 선택 대상에서 제외한다. 닉네임·목록 순서로 그룹장을 추정하지 않는다.
- 상단 인원은 서버의 그룹 전체 승인 인원인 `memberCount`를 사용한다. 그룹장 제외 후 선택 가능한 목록 길이와 혼동하지 않는다.
- 진입 시 양수 groupId, 현재 인증 사용자, 정상 소유 그룹 목록의 선택 유효성을 확인한다. 현재 소유 그룹 API는 myRole OWNER를 검증한다.
- 멤버 응답의 groupId 일치, 양수 사용자 ID·중복 ID·역할·online 자료형 등 계약을 검증한다. 현재 사용자의 OWNER 자격이 확인되지 않으면 선택을 차단하고 그룹 선택으로 돌아갈 안내를 제공한다. 알 수 없는 역할이나 깨진 응답을 정상 선택 대상으로 처리하지 않는다.
- 응답 메타데이터를 최종 표시 기준으로 사용한다. 그룹 선택에서 전달한 요약은 초기 문맥이며 조회 성공을 대신하지 않는다.

### 온라인 상태의 한계와 합의한 갱신

- `online`은 서버의 유효한 로그인 WebSocket 연결 존재 여부를 REST 조회 시점에 확인한 값이다. 사용자별 복수 연결을 허용하고 하나 이상이면 온라인이다. 단절 감지에는 지연이 있을 수 있다.
- 현재 서버는 멤버 접속 상태 변경 알림을 제공하지 않는다. 앱 수신부에도 해당 메시지 모델·구독은 없다. 초대 수신·참여 현황 메시지와 멤버의 온라인 상태 갱신은 다른 계약이다.
- **최초 진입 조회 + 사용자 새로고침 + 화면 활성 중 연결 복구 후 1회 재조회**로 갱신한다. 주기 폴링·새 메시지 규약·화면별 WebSocket 연결은 추가하지 않는다.
- 연결이 유지돼도 멤버 상태는 조회 시점 스냅샷이다. “접속 상태는 마지막 조회 기준입니다.” 안내와 새로고침을 제공하고, 실시간 상태로 표현하지 않는다.
- `AuthRepository.state`를 관찰하되 최초 CONNECTED와 최초 조회를 중복 실행하지 않는다. 실제 단절/재연결 후 CONNECTED 전환에 재조회하며 같은 연결 상태의 반복 방출에는 추가 조회하지 않는다.
- 재조회가 이미 진행 중이면 중복 실행하지 않는다. 요청 도중 연결이 끊겨 복구 전 요청이 된 경우 그 결과를 최신으로 승격하지 않고, 진행 요청 정리 후 복구에 따른 1회 조회로 대체한다. 요청 세대와 연결 유효성을 함께 확인한다.
- 로컬 연결 단절·재연결은 모든 멤버 오프라인을 의미하지 않는다. 마지막 성공 목록·스냅샷을 보존하되 현재 확인 불가 상태로 구분하고 “연결을 확인 중입니다. 접속 상태가 최신이 아닐 수 있습니다.”를 표시한다. 재확인 전 선택·완료는 제한한다.
- 재연결만으로 기존 스냅샷을 최신으로 바꾸지 않는다. 복구 후 조회 실패는 오류·재시도를 표시하며 확인 전 완료를 허용하지 않는다.

### 후속 초대 연결

- 초대 생성은 REST `POST /api/v1/ride-invitations`이다. 이후 서버 → 대상은 WebSocket `RIDE_INVITE`, 대상 → 서버의 수락/거절은 `RIDE_INVITE_RESPONSE`, 서버 → 그룹장의 현황은 `RIDE_INVITE_STATUS`이다.
- 후속 API는 그룹장·대상 모두 생성 시 온라인이어야 하고 대상 1~49명·승인 멤버·본인 제외·중복 제외를 요구한다. 스냅샷으로 향후 생성 성공을 보장하지 못하며 실제 생성 시 서버가 다시 검증한다.
- 이번에는 groupId와 선택 userId 목록을 후속 기능에 전달할 연결 지점만 남긴다. invitationId·초대 성공·대기 상태를 미리 만들거나 REST/소켓 발신을 연결하지 않는다.

## 4. 합의한 UI·선택 정책

### Figma 대응

- 풍경 배경, 뒤로 가기·‘멤버 선택’, 그룹 요약 카드(이름·총인원·설명), ‘멤버를 선택하세요.’, 흰색 멤버 목록, 하단 ‘선택 완료’를 구성한다.
- 행은 원형 선택 표시·닉네임·온라인 표시로 구성한다. 선택은 파란 원·흰 체크, 접속은 초록 점·‘접속 중’, 오프라인은 회색 점·‘오프라인’이다. 선택·접속 여부는 접근성 의미와 문구로도 전달한다.
- Figma 예시 인원·이름·선택은 Preview·테스트에만 사용한다. 예시 한 명 선택을 단일 선택 규칙으로 해석하지 않는다.
- HomeTheme·GroupDesign의 파란색 `#0683EA`, 회색, 10dp 모서리·공통 버튼을 우선 재사용한다. 그룹 선택의 원형 점과 이번 체크는 달라 무조건 재사용하지 않는다. 배경·뒤로 가기·인원 자산은 구현 시 일치 여부를 대조하고 차이가 있는 자산만 확보한다.
- Figma의 Roboto 지정과 기존 시스템 글꼴 차이는 렌더링에서 확인하고 남는 차이를 기록한다. 새 글꼴·라이브러리는 임의로 도입하지 않는다.
- 유연한 너비·필요한 최대 너비 제한·줄바꿈·안정적인 userId key의 Lazy 목록을 사용한다. 원본의 고정 좌표·목록 높이·전체 확대축소를 적용하지 않는다.
- 그룹 요약·목록·안내에 필요한 스크롤을 제공하고 하단 버튼과 마지막 항목이 겹치지 않게 한다. 시스템 인셋은 중복 없이 처리하고 버튼·행·뒤로 가기는 최소 48dp 터치 영역을 확보한다.
- 기본 Preview는 1개이며 추가 크기·확대 글꼴·상태 조합은 변경에 필요하거나 문제 발견 시에만 확인한다. 제품 문구는 문자열 리소스로 관리한다.
- 새로고침·스냅샷/불확실성 안내와 로딩·빈 결과·오류 UI는 Figma 외의 합의된 보완이다.

### 선택·완료와 상태별 동작

- 최초 무선택, 다중 선택을 허용한다. 선택된 온라인 행을 다시 누르면 해제한다. 최소 1명·최대 49명이며 자동 선택하지 않는다.
- 정상 조회로 확인한 현재 그룹의 OWNER·본인 제외 대상 중 `online == true`인 멤버만 선택할 수 있다. 오프라인도 목록에는 표시하되 선택 불가로 안내한다.
- 선택은 userId 집합으로 관리한다. 상한에서 추가 선택은 막고 최대 인원 안내를 제공한다. 닉네임을 키로 사용하지 않는다.
- 새로고침·재확인 중에는 진행 표시와 선택·완료 제한을 적용한다. 성공 시 기존 선택과 새 목록을 ID로 대조하고, 사라지거나 오프라인으로 바뀐 대상은 선택 해제 후 안내한다. 조회 사이의 변화는 감지할 수 없다.
- 현재 정상 목록·스냅샷, 앱 CONNECTED 상태, 유효한 선택 1~49명, 팝업 미표시 조건을 모두 만족할 때만 완료 가능하다. CONNECTED 자체가 멤버별 최신 상태의 증거는 아니다.
- 완료는 유효한 groupId와 중복 없는 사용자 ID들을 재검사한 뒤 **“라이딩 초대 기능은 개발 중입니다.”** 팝업만 표시한다. 팝업 닫기는 선택을 유지하고 다른 화면으로 이동하지 않는다.
- 팝업 중에는 선택·완료 중복 실행을 막는다. 팝업이 열린 동안 시스템 뒤로 가기는 팝업부터 닫는다.

## 5. 화면 이동·상태 수명·동시성

### 합의한 상태 수명

- 그룹 완료 시 현재 정상 소유 그룹 목록의 선택 ID와 인증 사용자·목적지를 확인하고 멤버 화면으로 1회 이동한다. 선택 그룹 ID가 필수이며 요약은 표시 보조로만 전달한다. JWT는 화면 상태에 넣지 않는다.
- **멤버 → 그룹:** 그룹 목록·선택·스크롤 위치를 유지한다. 멤버 조회·관찰 작업·목록·선택·팝업은 정리한다. 상단·시스템 뒤로 가기를 동일하게 처리한다.
- **멤버 재진입:** 같은 그룹이어도 최신 조회·무선택으로 시작한다.
- **다른 그룹 선택:** 이전 그룹의 요청·목록·선택·오류·팝업을 정리하고 새 그룹으로 진입한다.
- **그룹 → 메인:** 기존 정책대로 그룹 목록·선택과 멤버 문맥을 전부 초기화한다. 이후 메인에서 재진입하면 소유 그룹도 새로 조회한다.
- **구성 변경:** 같은 사용자·같은 진행 흐름의 상태와 선택을 보존하고 불필요한 중복 조회를 막는다. 앱 연결이 실제 복구된 경우에는 별도의 합의된 1회 재조회 정책이 적용된다. 프로세스 종료 뒤 선택 복원은 추가하지 않는다.
- **로그아웃·사용자 변경:** 요청 취소·관찰 중단·두 화면의 목록/선택/팝업과 선택 그룹 문맥을 정리한다. onCleared에만 의존하지 않는다.

기존 그룹 선택 계획은 모든 실제 화면 이탈에서 초기화했다. 멤버 왕복 보존은 이 정책의 **승인된 변경**이다. 1단계에서 멤버로 잠시 이동하는 경우와 선택 흐름 종료를 구분하고, 그룹 상태 초기화 책임과 목록 스크롤 상태를 두 화면의 부모 흐름으로 옮겼다. 0단계 당시에는 코드 동작을 바꾸지 않았다.

### 조회·관찰·중복 방지

- Route는 생명주기를 고려해 상태를 수집하고 화면 진입·이탈·사용자 이벤트만 연결한다. Screen은 UiState 표시와 콜백 전달, ViewModel은 Repository를 통한 조회·선택 조정을 담당한다.
- 현재 계약에는 멤버별 WebSocket 갱신이 없어 이벤트와 REST 멤버 목록을 병합하지 않는다. REST 멤버/온라인 스냅샷과 앱 공통 연결 상태를 함께 반영한다. 지원되지 않는 이벤트 캐시·병합 계층을 만들지 않는다.
- 활성 화면 여부·실행 중 Job으로 재구성·연속 진입·재시도·새로고침의 중복 조회를 막는다. 사용자·그룹·진입/요청 세대와 연결 유효성으로 늦은 응답을 차단한다. 취소는 기존 OkHttp 취소와 연결한다.
- 서버 목록을 ID 기준으로 교체하고 선택 집합을 재검증한다. 중복 응답·반복 연결 상태로 선택 해제 안내·복구 조회가 중복 발생하지 않게 한다.
- 현재 목적지·유효 선택·전환 진행 여부로 연속 완료 클릭의 중복 이동을 막는다. 인증 종료 뒤 이전 콜백이 화면을 다시 열지 않게 한다.
- 화면 이탈 시 멤버 화면 소유 요청·관찰 작업을 중단하되 앱 소유 로그인 WebSocket을 종료하거나 새로 만들지 않는다. 남아 있는 ViewModel의 세션 감시와 화면 활성 중 연결 상태 처리를 구분한다.

- [README의 서버 연결 설정](../README.md)에 따라 실제 서버 주소와 앱 ridesyncBaseUrl·연결 경로를 맞춘다. REST·WebSocket은 같은 ServerEndpoint 설정을 재사용한다. USB 디버깅만으로 네트워크 터널이 생기지는 않으며, 휴대폰 localhost 사용 시 기존 adb reverse 절차를 따른다.
- 가능하면 기존 그룹장 계정과 승인 멤버가 있는 그룹을 사용한다. 그룹장만 있는 그룹, 승인 대기·거절 사용자, 다른 멤버의 로그인 WebSocket 연결을 확인할 수 있는 환경은 해당 조건을 점검할 때만 준비한다. 이 작업에서 테스트 계정·그룹·DB 데이터를 새로 생성하거나 변경하지 않았다.
- 온라인/오프라인 확인은 다른 멤버의 로그인 WebSocket 연결 상태를 조절할 수 있는 환경에서만 추가한다. 본인 앱 연결 상태만으로 다른 멤버의 접속 여부를 판단하지 않는다. 네트워크 단절 후 서버의 종료 감지에는 지연이 있을 수 있다.
- 휴대폰 모델·Android 버전·앱 버전·세로 방향을 기록한다. 글꼴·시스템 내비게이션 방식은 문제 재현에 필요한 만큼만 기록하며 비밀번호·JWT는 기록하거나 캡처하지 않는다.

### 주요 흐름

| 순서 | 사용자 동작 | 기대 결과 |
|---|---|---|
| 1 | 로그인 → 라이딩 시작 → 소유 그룹 선택 → 완료 연속 누르기 | 멤버 화면 한 번 진입. 로딩 후 해당 그룹의 실제 승인 멤버 표시. 그룹장·본인은 행에서 제외하고 대기·거절 사용자는 포함하지 않음. 그룹 요약 총인원은 그룹장을 포함한 서버 값 |
| 2 | 최초 상태 확인 → 온라인 멤버 선택·해제·다중 선택 → 오프라인 행 누르기 | 최초 자동 선택 없음. 유효한 온라인 대상 1명 이상일 때만 완료 활성화. 오프라인은 표시하되 선택 불가. 상한 49명은 자동 테스트로 검증했으므로 이를 확인하기 위해 대량 계정을 만들 필요 없음 |
| 3 | 선택 완료 연속 누르기 → 팝업 확인/시스템 뒤로 가기로 닫기 | “라이딩 초대 기능은 개발 중입니다.” 팝업 하나만 표시. 초대 전송·다음 화면·라이딩 시작 없음. 닫으면 선택 유지 |
| 4 | 상단/시스템 뒤로 가기로 그룹 복귀 → 같은 그룹 또는 다른 그룹으로 재진입 → 그룹에서 메인 복귀 후 재진입 | 그룹 복귀는 목록·선택·스크롤 유지. 멤버 재진입은 최신 조회·무선택이고 다른 그룹의 이전 멤버/선택이 남지 않음. 메인 이탈 후에는 그룹도 새 조회·무선택 |
| 5 | 멤버 화면에서 새로고침, 가능하면 선택 멤버의 연결 종료 후 새로고침 | 조회 중 선택·완료·중복 새로고침 제한. 서버가 오프라인 또는 목록 제외로 반환하면 해당 선택 해제·안내. 정상 조회 후에도 접속 상태는 조회 시점 기준이며 자동 변경 알림으로 오해하지 않음 |
| 6 | 앱 네트워크 단절 → 연결 복구, 가능하면 백그라운드 이동 후 복귀 | 단절·재연결 중 과거 스냅샷을 전원 오프라인으로 바꾸지 않고 확인 불가로 표시. 완료 제한. 복구 후 새 조회 성공으로 상태 재확인. 실패하면 오류·재시도 제공 |

### 환경이 가능한 경우에만 추가 확인

- 그룹장만 있는 그룹: “함께 라이딩할 멤버가 없습니다.”와 비활성 완료. 선택 대상은 있으나 모두 오프라인이면 목록과 “현재 접속 중인 멤버가 없습니다.” 표시. 조회 실패를 이 정상 빈 상태로 바꾸지 않아야 한다.
- 조회 실패·재시도: 이전 성공 결과가 있으면 과거 상태로만 보존하고 완료를 제한한다. 403·404·OWNER 자격 미충족이면 선택·과거 멤버를 정리하고 그룹 선택 복귀를 안내한다. 권한 변화를 만들기 위해 임의 DB 수정을 할 필요는 없다.
- 화면 이탈·사용자 변경: 조회 중 그룹으로 돌아오거나 메인 복귀 후 로그아웃·다른 계정 로그인 시 이전 목록·선택·팝업이 되살아나지 않아야 한다. 401·토큰 만료는 재현 가능한 경우에만 확인하며 이를 위해 인증 설정을 바꾸지 않는다.
- 목록이 길거나 닉네임·그룹명이 긴 경우: 끝까지 스크롤해 마지막 행·안내·하단 버튼 접근성을 확인한다. 구성 변경·확대 글꼴은 필요한 경우에만 추가하며 정상 재구성과 실제 화면 이탈의 정책을 구분한다.

### 결과 기록과 후속 연결

이 문서에 날짜·기기/OS·앱 버전·실제 확인한 흐름·결과를 짧게 덧붙인다. 실제 서버 조회와 UI 조작 성공을 나누고, 실패는 재현 순서·미실행 이유를 기록한다. 아직 실행하지 않은 항목을 통과로 표시하지 않는다.

후속 초대 기능의 입력은 현재 멤버 상태의 groupId와 선택 userId 집합이다. 별도 승인 후 REST 초대 생성과 기존 로그인 WebSocket의 초대 수신/응답·현황 파싱을 연결해야 한다. 현재 스냅샷은 향후 초대 성공의 증거가 아니므로 생성 시 서버 결과를 다시 처리해야 한다. 이번 인수인계에서는 해당 기능을 구현하지 않았다.
