# RideSync Android UI 구현 지침

## 1. 목적과 적용 범위

이 문서는 Figma 디자인을 Kotlin·Jetpack Compose UI로 구현할 때 적용하는 상세 기준이다.
특정 Figma 프레임이나 휴대폰 크기에 화면을 고정하지 않고, 실제 앱 창의 크기와 사용자 설정에 맞게 콘텐츠를 배치한다.
상위 개발 원칙은 [AGENTS.md](../AGENTS.md), 프로젝트 구조와 실행 방법은 [README.md](../README.md)를 따른다.

이 문서는 앞으로의 구현·검증 기준이며, 기존 화면이 모든 기준을 충족했다는 검증 기록이 아니다.
앱 코드 변경은 사용자가 승인한 화면과 단계에 한정한다.

## 2. 현재 기반과 지원 범위

- Kotlin, Jetpack Compose, Material 3 및 단일 app 모듈을 사용한다.
- feature-first + MVVM + Repository 구조와 AppContainer 기반 의존성 주입을 유지한다.
- MainActivity는 edge-to-edge를 사용하므로 시스템 영역과 콘텐츠의 관계를 화면마다 확인한다.
- 기존 연결 테스트 화면은 가변 너비, 최대 너비 600dp, 스크롤 및 키보드 여백을 사용한다. 이 수치는 모든 제품 화면의 공통 규격이 아니다.
- 기존 테마는 시스템 다크 모드와 동적 색상을 사용한다. Figma 색상과 일치시키기 위한 정책은 화면 구현 계획에서 확인하고 승인 범위 내에서 반영한다.

지원 대상은 Android 휴대폰의 세로 화면이다(2026-11-07 사용자 결정). 태블릿·가로 화면 전용 설계와 검증은 기본 작업 범위에서 제외한다.
우선 확인 기기는 사용자의 갤럭시 S26+와 갤럭시 S10 5G이다. 팀원들도 Android 휴대폰을 사용하며 정확한 모델과 제조사, 각 기기의 Android 버전은 아직 확인하지 않았다. 팀원 기기는 실제 정보가 확인되면 최종 점검에 포함한다.

화면마다 하나의 유연한 Compose UI를 구현한다. 여러 Preview는 같은 화면의 개발용 확인 조건이며, 기기별로 별도 UI를 만들거나 모든 기기를 지원한다는 의미가 아니다.
가변 너비, 필요한 스크롤, 키보드·시스템 바 인셋, 글꼴 확대에 대한 기본 대응은 유지한다.

세로 화면 지원 결정 자체가 Android 회전 잠금의 구현 완료나 코드 변경 승인을 의미하지 않는다. Manifest/Activity의 방향 설정은 해당 변경이 승인된 구현 범위에 포함될 때 반영한다.
제품 전체의 다크 모드 지원 범위는 미확정이며, 화면별로 승인된 테마 정책을 따른다.

## 3. Figma를 구현으로 옮기는 절차

1. URL의 파일·프레임·노드와 구현할 화면 범위를 확인한다.
2. 색상, 타이포그래피, 간격, 정렬, 모서리, 이미지, 컴포넌트 변형 및 Auto Layout 의도를 확인한다.
3. 화면을 상단 영역, 본문, 스크롤 영역, 하단 동작 영역 등으로 나누고 각 영역의 크기 규칙을 정한다.
4. 기존 테마와 공통 컴포넌트로 표현할 부분과 해당 기능 전용 요소를 구분한다.
5. UI 상태, 화면 이동, API 연동 및 검증 계획을 제시하고 승인한 단계만 구현한다.

Figma의 px 값을 기기 물리 픽셀에 그대로 적용하지 않는다. 프레임 전체를 기기 폭의 비율로 확대·축소하지도 않는다.
개별 디자인 수치를 dp/sp 기준으로 해석하되 텍스트 길이, 시스템 설정, 가용 공간에서 적절한지 확인한다.
예를 들어 폭 390의 프레임에 좌우 여백이 있는 입력 폼은 화면 폭을 390dp로 고정하지 않고, 가용 너비에서 좌우 여백을 제외한 폭을 사용한다.

화면 캡처 안의 상태 표시줄이나 키보드는 일반적으로 운영체제가 제공하는 영역이다. 별도 제품 요구가 없다면 앱 UI로 복제하지 않는다.
원본 아이콘·이미지 자산을 우선 사용하며, 자산이나 폰트가 없으면 대체 사실과 시각적 차이를 알린다.
Figma에 없는 동작은 [서버 API 명세](../../server/docs/API_SPEC.md)와 요구사항을 확인한다. 그래도 불명확한 동작은 질문한다.

## 4. 레이아웃과 크기 규칙

| 요소 | 구현 기준 |
|---|---|
| 화면 루트 | 현재 앱 창과 부모의 제약을 기준으로 크기 결정 |
| 본문·입력 폼 | 가변 너비와 좌우 여백 사용, 필요하면 최대 너비 제한 후 중앙 정렬 |
| 아이콘·간격 | 디자인에 맞는 dp 기준값 사용, 화면 폭에 비례해 무조건 확대하지 않음 |
| 버튼·입력란 | 최소 크기를 확보하고 글꼴 확대나 안내 문구에 따라 높이 증가 허용 |
| 카드·목록 행 | 콘텐츠에 맞춰 높이 결정, 텍스트가 늘어도 겹치지 않게 구성 |
| 이미지 | 목적에 맞는 종횡비와 맞춤·잘라내기 정책 적용 |
| 남는 공간 | 적절한 가중치·정렬로 배분, 필수 콘텐츠를 밀어내지 않도록 확인 |

- Row, Column, Box를 우선 활용하고 단순 배치를 절대 좌표나 offset으로 구성하지 않는다.
- 장식이나 실제 중첩이 필요한 요소에만 제한적으로 겹침 배치를 사용한다.
- 작은 화면에서는 여백 조정, 줄바꿈, 세로 배치 전환, 스크롤 순으로 적합한 방식을 선택한다. 글자를 무조건 줄여 맞추지 않는다.
- 가로 버튼 여러 개가 들어가지 않으면 세로 배치나 다른 적절한 구성을 사용한다.
- 레이아웃 전환 기준은 기기 모델명이 아닌 가용 공간과 콘텐츠 요구로 정한다.
- 휴대폰에서는 단일 열과 필요한 최대 너비 제한을 우선 사용한다. 태블릿·가로 화면용 재배치나 다중 열 설계를 기본 작업에 추가하지 않는다.
- Modifier의 순서에 따라 크기·여백 적용 결과가 달라질 수 있으므로 최종 측정 결과를 확인한다.

## 5. 스크롤과 하단 버튼

- 짧은 폼도 작은 화면·키보드·글꼴 확대 시 높이가 부족하면 스크롤할 수 있어야 한다.
- 긴 목록은 LazyColumn 등 적절한 Lazy 구성으로 구현하고 안정적인 항목 식별자를 사용한다.
- 같은 방향의 스크롤 컨테이너를 제약 없이 중첩하지 않는다. 가능한 한 하나의 주 스크롤 영역으로 구성한다.
- 하단 버튼을 고정할지 본문과 함께 스크롤할지는 화면의 디자인과 동작 목적에 따라 결정한다.
- 고정 버튼 영역의 실제 높이와 시스템 여백을 고려해 본문 공간을 확보한다.
- 마지막 목록 항목, 오류 문구, 필수 입력란이 버튼 뒤에 가려지지 않는지 끝까지 스크롤해 확인한다.
- 글꼴 확대 때문에 고정 영역이 대부분의 화면을 차지하면 버튼도 스크롤에 포함하는 등 접근 가능한 배치를 선택한다.

## 6. 시스템 영역과 키보드

- 배경은 시스템 영역까지 이어질 수 있지만 텍스트와 터치 대상은 가려지지 않도록 배치한다.
- 상단 바, 본문, 하단 바 중 어느 영역이 시스템 인셋을 처리하는지 명확히 한다.
- Scaffold의 innerPadding을 적용하고 자식이 같은 인셋을 다시 더하지 않도록 인셋 소비 여부까지 점검한다.
- 시스템 바 높이를 상수로 넣거나 기기 모델별 보정값으로 처리하지 않는다.
- 제스처 내비게이션과 버튼 내비게이션에서 하단 콘텐츠와 터치 영역을 확인한다.
- 키보드 표시 시 IME 인셋을 고려하고 포커스된 입력란, 오류 문구, 제출 동작에 접근 가능하게 한다.
- imePadding을 모든 계층에 일괄 추가하지 않는다. 실제 여백 담당 위치를 정해 중복 공간을 방지한다.
- 키보드를 닫은 뒤 과도한 빈 공간이 남거나 화면 위치가 잘못 유지되지 않는지 확인한다.
- 뒤로 가기와 키보드의 다음·완료 동작이 의도한 흐름과 일치하는지 확인한다.

## 7. 텍스트·이미지·접근성

- 글자는 sp와 공통 typography를 사용하고 시스템 글꼴 배율을 임의로 무력화하지 않는다.
- 본문, 오류 안내, 버튼 문구를 담은 컨테이너에 불필요한 고정 높이를 주지 않는다.
- 긴 한글·영문 이름, 공백 없는 문자열, 여러 줄 오류 문구를 시험한다.
- 보조 정보는 필요에 따라 말줄임할 수 있지만 핵심 정보는 줄바꿈이나 상세 표시로 확인할 수 있게 한다.
- 입력란은 힌트만으로 의미를 전달하지 않고 적절한 라벨과 오류 안내를 제공한다.
- 이미지의 비율을 유지한다. 아바타는 필요한 잘라내기를 허용하되 로고·안내 이미지는 핵심 부분이 잘리지 않도록 한다.
- 색상만으로 성공·실패·선택 상태를 전달하지 않고 텍스트나 형태를 함께 사용한다.
- 터치 대상은 원칙적으로 최소 48dp를 확보한다. 시각적 아이콘 크기와 터치 영역을 구분한다.
- 기능 아이콘에는 의미 있는 접근성 설명을 제공한다. 장식 이미지는 중복 안내를 피한다.
- 기본 및 지원하는 테마에서 글자와 배경의 구분, 포커스 순서, 스크린리더의 주요 동작 안내를 점검한다.
- 제품 문구는 문자열 리소스로 관리하고 기존 한국어 표현을 일관되게 사용한다.

## 8. 디자인 시스템과 코드 책임

- 색상, typography, 공통 모양은 core/designsystem의 테마를 통해 관리한다.
- 여러 화면에서 반복되는 의미 있는 컴포넌트만 공통화한다. 화면별 미세한 차이를 과도한 옵션으로 합치지 않는다.
- 기능 전용 컴포넌트는 해당 feature의 presentation 아래에 둔다.
- Route는 상태 수집과 이벤트 연결, Screen은 UiState 렌더링과 콜백 전달을 담당한다.
- ViewModel은 상태와 비즈니스 동작을 조정하고 Repository 인터페이스를 통해 데이터에 접근한다.
- 네트워크 연결, 토큰 처리, WebSocket 연결 생성은 UI 렌더링 코드에 넣지 않는다.
- 단순 UI 상태와 서버 상태를 구분한다. 화면 재생성이나 재진입 시 보존할 입력값과 다시 조회할 데이터를 명시한다.
- 미리보기는 샘플 UiState와 콜백으로 구성하며 서버 접속이나 실제 데이터 변경을 하지 않는다.

## 9. 상태별 화면과 상호작용

| 상태 | 확인 기준 |
|---|---|
| 초기·로딩 | 진행 중임을 알리고 중복 요청 방지 |
| 정상 | 실제 데이터 표시, 가능한 동작과 권한 반영 |
| 빈 결과 | 오류와 구분하고 필요한 다음 동작 안내 |
| 입력 오류 | 해당 입력과 연결된 안내, 수정한 값 유지 |
| 요청 실패 | 실패 사실과 가능한 복구 방법 표시, 성공 화면으로 이동하지 않음 |
| 연결 끊김·재연결 | 최신 상태가 아닐 수 있음을 표시하고 서버와 재동기화 |
| 만료·종료·권한 변경 | 서버 결과를 반영하고 불가능한 동작 제한 |

오류 메시지가 추가되어도 입력란과 버튼 배치가 깨지지 않아야 한다.
재시도는 API의 특성을 고려하며 데이터 변경 요청을 무조건 반복하지 않는다.
초대·라이딩 등 실시간 상태가 변경될 때 현재 화면과 이동 흐름이 일치하는지 확인한다.

## 10. 화면 검증 조건

### 기본 확인

- 화면당 기본 Compose Preview 1개를 만든다. Figma의 세로 프레임 또는 확인된 휴대폰 앱 창 크기를 참고하며, Preview 치수를 실제 UI의 고정 크기로 사용하지 않는다.
- 기본 Preview에서 디자인과 주요 배치를 확인하고, 변경 범위에 맞는 빌드·lint를 수행한다. Preview 정의와 실제 렌더링 확인은 구분한다.
- 실기기 점검은 S26+와 S10 5G의 세로 화면을 중심으로 주요 조작 흐름을 확인한다. 모든 소규모 수정마다 두 기기에서 전체 검증을 반복할 필요는 없다.
- 기존 로그인·연결 화면에 여러 Preview가 있어도 이후 화면에서 그대로 복제하지 않는다. 기존 Preview 삭제는 별도 코드 변경 범위이며, 과거 검증 기록은 당시 수행 사실로 보존한다.

### 필요한 경우에만 추가 확인

아래 항목은 매번 전부 실행하는 체크리스트가 아니다. 변경 내용 또는 발견한 문제와 관련된 조건만 선택하며, 추가 확인을 위해 반드시 영구적인 Preview 함수를 만들 필요는 없다.

| 조건 | 확인 목적 |
|---|---|
| 좁은 휴대폰 창(예: 320×640dp) | 배치·크기 변경 시 버튼과 텍스트 접근성 |
| 확대 글꼴(예: 1.3 또는 2.0) | 텍스트·고정 영역 변경 시 줄바꿈과 필수 동작 접근성 |
| 키보드 열림·닫힘 | 입력 폼·인셋 변경 시 포커스 입력란, 제출 및 스크롤 |
| 긴 데이터·빈 데이터·오류 | 해당 상태의 표시를 추가·변경할 때 배치 변화 |
| 화면 재생성·재진입 | 상태 보존·생명주기 변경 시 입력 유지와 중복 요청 여부 |
| 팀원 Android 휴대폰 | 모델·OS 확인 후 최종 시연 점검 또는 기기별 문제 재현 |

좁은 창과 큰 글꼴의 조합은 관련 문제가 있거나 레이아웃상 확인이 필요한 경우에만 사용한다. 태블릿·가로 화면 및 모든 조건의 조합을 기본 검증에 포함하지 않는다.
실기기에서는 모델명과 Android 버전을 기록하고, 글꼴·디스플레이 크기·내비게이션 방식은 검증이나 문제 재현에 필요한 만큼 기록한다.
픽셀 단위 스크린샷 크기를 dp 크기로 오인하지 않는다.

### 반복 작업과 컨텍스트 사용

- 새 세션에서는 관련 지침과 현재 구현을 확인하되, 같은 작업에서 이미 읽은 문서·디자인은 변경되거나 추가 정보가 필요할 때 관련 부분만 다시 확인한다.
- 최초에는 기본 화면을 중심으로 확인하고, 실패·시각적 차이·추가 변경이 있을 때 필요한 조건으로 검증을 넓힌다.
- 단순 수정마다 전체 화면 조건의 캡처나 UI 자동화를 반복하지 않는다. 도구 출력과 스크린샷도 판단에 필요한 범위로 제한한다.
- 검증 기록은 변경 내용, 실제 확인 조건·결과, 남은 문제를 간단히 적는다. 화면마다 새 문서나 상세 기기 정보 표를 의무적으로 만들지 않는다.

### 완료 기준

- 의도하지 않은 텍스트 잘림, 겹침, 화면 밖 배치가 없다.
- 모든 필수 정보와 주요 버튼에 직접 또는 스크롤로 접근할 수 있다.
- 시스템 영역, 키보드, 고정 버튼이 콘텐츠를 가리지 않는다.
- Figma와 다른 부분은 화면 적응이나 접근성 등 이유를 설명할 수 있다.
- 주요 UI 상태와 동작을 확인하고, 검증하지 못한 조건을 명시한다.

빌드·정적 분석은 변경 범위에 맞게 수행한다. 프로젝트의 기본 명령은 다음과 같다.

```powershell
.\gradlew.bat :app:assembleDebug :app:lintDebug
```

빌드 성공은 화면 검증 완료가 아니다. Preview, 에뮬레이터, 실기기, 실제 서버 연동 결과를 각각 보고한다.
문서만 변경한 경우에는 앱 빌드를 실행하지 않고 내용과 참조를 확인한다.

### 화면별 검증 기록 양식

아래는 필요한 항목만 선택하는 참고 양식이다. 간단한 변경은 기존 관련 기록에 짧게 추가할 수 있으며, 모든 칸을 채우거나 별도 캡처 파일을 만들 필요는 없다.

```text
화면 / Figma URL·노드:
승인한 구현 범위:
기기 또는 Preview 조건:
Android 버전 / 앱 창 크기 / 글꼴·디스플레이 설정:
방향 / 시스템 내비게이션 / 키보드 상태:
검증한 UI 상태와 동작:
Figma 대비 차이와 사유:
빌드·정적 분석 결과:
시각적 확인 결과 및 캡처 위치:
미검증 항목 / 남은 문제:
```

민감한 계정 정보나 토큰을 검증 기록과 스크린샷에 포함하지 않는다.
