# 라이딩 초대·참여 현황·시작/취소 개발계획

## 1. 승인 범위와 현재 상태

- 기준일: 2026-11-18. 사용자는 권장 정책 합의와 0·1단계 완료 후 **2-A 공통 소켓·초대 생성·리더 현황, 2-B 멤버 초대 수신·응답, 2-C 시작·취소·임시 주행 이동을 각각 추가 실행 승인**했고, 이어서 3단계 자체 점검·인수인계를 승인했다.
- 0단계: 완료. 이 계획 작성과 멤버 선택 계획의 후속 문서 연결만 수행했다.
- 1단계·2-A·2-B·2-C: 구현·가능한 자체 검증 완료. 실제 검증과 완료 기록은 8절을 따른다. 3단계 자체 점검·인수인계도 완료했다. 실제 Spring 서버·실기기 확인은 남아 있으며 9절 절차를 따른다.
- 현재 앱은 멤버 선택 완료에서 초대 생성 REST를 요청하고 201 확인 후 메인·리더 현황 팝업으로 이동한다. 기존 로그인 WebSocket의 현황을 초대 ID별로 반영하고 리더 ID를 제외해 집계한다. 실패·결과 불명확·연결 단절은 성공으로 대체하지 않는다.
- 그룹원의 초대 자동 팝업·수락/거절 발신은 2-B에서 연결했다. 전송됨과 서버 확정을 구분하며 불명확 상태에서는 다른 초대 응답을 제한한다. 2-C에서 시작/취소 REST·알림을 연결했다. 최신 현황·연결·요청 상태로 버튼을 제한하고 서버 시작 확정과 명확한 초대/역할 문맥으로만 임시 주행 화면을 연다. 모호한 자동 이동·정리는 보류한다. 실제 주행 종료 기능은 범위 밖이다. 샘플은 Preview·테스트에만 있다.
- Kotlin·Compose·Material 3, feature-first MVVM·Repository·AppContainer를 유지한다. 새 라이브러리·불필요한 계층·무관한 리팩터링은 추가하지 않는다.
- 서버 코드·설정·DB, 앱 주소 설정, 커밋·푸시·브랜치 변경은 범위 밖이다. 동시 초대도 서버·DB 변경 없이 앱 메모리의 최소 처리만 한다.

목표는 **멤버 선택 → REST 초대 생성 → 성공 확인 후 메인·리더 현황 팝업 → 멤버의 WebSocket 초대 수신·응답 → 서버 시작 성공에 따른 역할별 임시 주행 화면**이다. 시작 전 취소도 포함한다. 수락은 라이딩 참여 응답이며 그룹 가입 처리와 무관하다.

주행 화면은 “선두 주행 화면” 또는 “후미 그룹 주행 화면” 텍스트만 표시한다. 지도·위치·수신호·속도·실시간 주행 소켓·종료·기록·백그라운드 푸시는 구현하지 않는다.

## 2. 확인 근거와 현재 연결 지점

- 같은 채팅의 선행 계획 검토에서 [AGENTS.md](../AGENTS.md), [README.md](../README.md)의 구조·연결 정보, [UI 지침](APP_UI_GUIDELINES.md), [멤버 선택 계획](MEMBER_SELECTION_DEVELOPMENT_PLAN.md)의 승인·현재 상태·검증·후속 연결을 확인했다.
- 계약 원본은 [서버 API 명세](../../server/docs/API_SPEC.md)의 8.2~8.5, 9.1~9.4, 로그인 WebSocket, 13.4~13.5, 14절이다. 이 문서는 앱 적용 정책을 기록하며 요청·응답 명세의 별도 관리본을 만들지 않는다.
- 시작 알림·응답 확정의 식별 정보가 부족하여 명세 10.1과 서버의 `LoginWebSocketHandler.handleTextMessage`, `RideInvitationService.respond`, `RideStartedMessage`, `WebSocketErrorMessage` 관련 부분만 추가 확인했다. 성공 ACK 부재와 식별 필드 부재는 구현에서도 확인했다. DATABASE.md와 무관한 서버 구현·과거 인증/알림 검증 문서는 열지 않았다.

## 3. Figma와 합의한 UI 정책

### 디자인 대응

- [리더 참여 현황](https://www.figma.com/design/vdeCHSAx4g9YRVDcyfF7Sh/RideMate--Copy-?node-id=335-96), `335:96`: 메인 위 어두운 배경, 둥근 흰 패널, 라이딩 아이콘, “라이딩 요청을 대기중입니다.”, 요청·수락·대기·거절 집계, 왼쪽 “라이딩 취소”·오른쪽 “라이딩 시작”. 개별 참여자 목록은 없으며 임의 추가하지 않는다.
- 사용자가 제공한 [멤버 링크](https://www.figma.com/design/vdeCHSAx4g9YRVDcyfF7Sh/RideMate--Copy-?node-id=279-143)의 `279:143`은 배경 오버레이다. 상위 [수신 팝업](https://www.figma.com/design/vdeCHSAx4g9YRVDcyfF7Sh/RideMate--Copy-?node-id=279-64), `279:64`를 확인했다. “라이딩 참여 요청이 왔습니다.”, 그룹명·리더 정보, 왼쪽 거절·오른쪽 수락을 반영한다.
- 예시 이름·집계 숫자·진행 상태는 Preview·테스트 전용이다. 실제 성공·참여 상태로 사용하지 않는다.
- HomeTheme·GroupDesign의 `#0683EA`, 회색 패널·버튼 표현을 재사용한다. 팝업 전용 라이딩 아이콘은 기존 자산과 대조하고 정확히 일치하지 않는 자산만 구현 시 확보한다. 기존 메인 배경 전체를 새로 만들지 않는다.
- 약 321px 패널, 20px 모서리, 38px 버튼 높이는 디자인 참고다. 가용 너비·필요한 최대 너비·줄바꿈·스크롤·인셋으로 배치하고 터치 영역은 최소 48dp를 확보한다. 전체 확대축소·기기별 고정 보정은 하지 않는다.
- Roboto 지정과 기존 시스템 글꼴 차이를 렌더링에서 확인한다. 새 폰트·라이브러리를 임의 도입하지 않는다. 제품 문구는 문자열 리소스로 관리한다.

### 사용자와 합의한 동작

- 초대 수신은 현재 인증 화면 위에서 자동 표시한다. 앱이 포그라운드이고 기존 로그인 WebSocket이 연결된 경우가 대상이다. 백그라운드 수신·푸시는 제공하지 않는다.
- 팝업 바깥 터치는 무시한다. 시스템 뒤로 가기·“나중에 보기”는 표시만 접고 서버 취소·거절을 보내지 않는다. 메인에 초대/대기 상태를 다시 여는 진입점을 둔다.
- 수락 후에는 “수락 응답을 보냈습니다. 시작 알림을 기다리는 중입니다.”와 서버 확정 확인 불가 안내를 표시한다. 거절도 “거절 응답 전송됨”으로만 표시하며 확정 완료로 꾸미지 않는다.
- 리더 취소는 실제 취소 버튼으로만 수행한다. 취소 REST 성공 또는 일치하는 취소 알림을 확인하면 리더 현황을 정리하고 메인을 유지한다. 멤버는 해당 초대만 정리하고 취소 안내 후 기존 화면을 유지한다.
- 임시 주행 화면의 뒤로 가기는 메인 이동이며 라이딩 종료가 아니다. 같은 로그인 세션에서 해당 임시 주행 화면을 다시 열 수 있다. 종료 API는 호출하지 않는다.
- 동시 초대는 MVP 핵심 범위로 확대하지 않는다. 초대 ID별 중복 방지·메모리 보관·한 번에 하나씩 순차 표시만 한다. 별도 초대 관리 화면·서버 동시 초대 제한·DB 저장은 추가하지 않는다.
- 응답 결과가 불명확한 동안 다른 초대의 응답을 제한하고 안내한다. 시작 알림의 초대 연결·역할이 모호하면 자동 이동을 보류한다. 알림이 왔다는 이유로 다른 초대 상태를 지우지 않는다.
- 기존 메인 알림·새 초대·대기 팝업은 중첩하지 않는다. 이미 표시 중인 팝업을 새 초대로 교체하지 않고 대기시켜 조작 대상을 유지한다. 시작·취소 확정 이벤트는 공통 상태에 즉시 반영한다.

## 4. 계약 적용과 확인 불가의 경계

| 흐름 | 앱 적용 |
|---|---|
| 초대 생성 REST | 201 및 유효한 생성 응답을 확인한 뒤 메인 이동. 생성 요청과 WebSocket 알림을 별개로 처리 |
| RIDE_INVITE | 초대 ID로 중복 방지하고 그룹·리더 정보를 표시 |
| RIDE_INVITE_RESPONSE | 기존 소켓으로 명세 형식의 boolean 응답 전송. 그룹 가입 API를 호출하지 않음 |
| RIDE_INVITE_STATUS | 리더의 전체 참여 목록으로 교체. 현황 GET·별도 소켓·폴링을 추가하지 않음 |
| 시작 REST·RIDE_STARTED | 서버 시작 확정 근거를 사용하고 rideSessionId별 한 번만 이동 |
| 취소 REST·RIDE_INVITE_CANCELLED | invitationId가 일치하는 상태만 한 번 정리 |

- 서버 acceptedCount는 리더를 포함한다. 생성자의 인증 사용자 ID를 리더 ID로 보관하고 participants에서 해당 ID를 제외해 요청·수락·대기·거절을 집계한다. 닉네임·순서로 추정하지 않는다. 수락 0명인 최초 상태와 서버 acceptedCount=1을 혼동하지 않는다.
- 최신 유효 현황의 canStart와 현재 요청·연결 상태로 시작 버튼을 제한한다. 서버 canStart는 온라인 수가 아니며 실제 시작 허용은 시작 API가 최종 결정한다. 리더 포함 2명 이상이라는 조건을 UI 집계에 맞춰 재정의하지 않는다.
- 응답 성공 ACK가 없고 현황은 리더에게만 전달된다. WebSocket send 성공은 로컬 전송 접수일 뿐 서버 수락·거절 확정이 아니다. ERROR 미수신·시간 경과·재접속 후 초대 미수신도 성공 근거가 아니다.
- ERROR에는 invitationId·요청 ID가 없다. 한 번에 하나의 응답 발신으로 제한하더라도 늦은 오류의 귀속이 항상 보장되지는 않는다. 확실히 연결할 수 없는 ERROR는 공통 안내로 처리하며 특정 초대를 종료하거나 성공 처리하지 않는다. 시간 초과로 요청 귀속이 모호해진 뒤 새 요청에 이전 오류를 붙이지 않는다.
- RIDE_STARTED는 invitationId·리더 ID·역할이 없다. 기존 주행 GET도 역할을 주지 않는다. 시작 REST 문맥의 리더, 또는 유일하고 모순 없는 초대 문맥의 멤버처럼 역할을 확인할 근거가 있을 때만 LEADER/MEMBER를 정한다. 같은 그룹의 여러 초대·역할 충돌 등 불명확한 경우 그룹 ID만으로 추정하지 않고 자동 이동을 보류한다.
- 재접속 RIDE_INVITE_STATUS에는 그룹·리더 메타데이터가 없다. 알고 있는 초대 ID와만 합치고 모르는 그룹·초대 대상을 목록 순서나 닉네임으로 복원하지 않는다. 알 수 없는 현황 ID는 생성 요청의 성공으로 임의 귀속하지 않는다.
- 만료는 서버 생성 후 30분이지만 메시지에 생성·만료 시각이 없다. 수신 시각부터 임의 카운트해 서버 만료로 확정하지 않는다. 서버 재시작·만료 통지, 취소/시작의 오프라인 보관·재전송도 없다.
- 재접속 복구는 리더의 유효 초대 현황과 멤버의 유효 PENDING 초대만이다. ACCEPTED/REJECTED 본인 확정 동기화와 복구 완료 신호가 없으므로 메시지가 없다는 이유로 기존 대기를 취소·만료·시작 상태로 바꾸지 않는다. 확인할 수 없는 상태를 명시하고 표시를 접을 수 있게 한다.
- 서버·DB 변경 없는 이번 MVP에서는 모든 다중 연결·동시 초대·알림 유실의 확정 복구를 보장하지 않는다. 이 한계를 숨기기 위한 새 API·추정 성공·자동 재전송은 추가하지 않는다.

## 5. 상태 소유·요청·화면 이동

### 소유자와 수명

- AppContainer가 초대 Repository를 제공한다. 인증 영역에서 유지되는 초대 ViewModel이 초대별 상태·진행 요청·표시 대기열을 관리한다. 구성 변경은 유지하고 단순 화면 이동으로 수신 관찰을 중단하지 않는다.
- LoginSession이 연결·인증과 유효한 메시지/발신 경계를 소유한다. 인증·연결 세대 검사를 통과한 메시지만 초대 상태에 반영한다. 화면마다 새 연결을 만들거나 UI에서 네트워크를 호출하지 않는다.
- Route는 생명주기를 고려한 수집·이벤트 연결, Screen은 상태 표시·사용자 이벤트만 담당한다. 재구성·재수집으로 생성/응답 요청이나 이동을 반복하지 않는다. 유실되면 안 되는 초대 상태는 일시적인 UI 이벤트만으로 운반하지 않는다.
- 화면 이탈로 멤버 선택이 정리되더라도 이미 확인한 초대는 인증 영역 상태에 먼저 넘긴다. 현재 그룹 복귀의 목록·선택·스크롤 유지와 멤버 재진입의 새 조회·무선택 정책을 유지한다.
- 백그라운드에서는 기존 연결 종료·복귀 시 재연결 정책을 유지한다. 마지막 상태를 보존하되 현재 확인 불가로 표시하고 변경 동작을 제한한다. 연결 단절은 거절·취소·참여 해제가 아니다.
- 로그아웃·만료·사용자 변경 시 요청·관찰·대기열·팝업·주행 문맥과 중복 처리 기록을 정리하고 이전 사용자 콜백을 무효화한다. 프로세스 재시작은 기존 세션 정리·재로그인 정책을 유지하며 초대 영구 저장을 추가하지 않는다.

### 생성과 리더 현황

- 완료 시 현재 인증 사용자·연결·유효 스냅샷·양수 그룹 ID·온라인 선택 1~49명을 확인하고 ID 집합을 복사한다. 진행 중 선택 변경·완료 중복·화면 이탈을 제한한다.
- 201 응답을 확인하면 초대 상태를 저장한 뒤 메인으로 한 번 이동하고 리더 현황을 표시한다. 현황이 아직 없으면 “참여 현황 확인 중”이며 임의의 0명 집계나 시작 가능 상태를 만들지 않는다.
- REST보다 현황이 먼저 오면 invitationId별로 보관하고 생성 응답의 같은 ID와 합친다. 오래된 초기 상태로 이미 받은 최신 현황을 덮지 않는다.
- 명확한 실패는 선택 화면을 유지한다. USER_OFFLINE·INVALID_INVITEE는 재조회·선택 재확인을 안내하고, 403·그룹 없음은 그룹 복귀, 401은 기존 세션 종료 경계를 사용한다. 실패를 빈 결과나 생성 성공으로 바꾸지 않는다.
- 생성 POST 재호출은 새 초대다. 타임아웃·응답 단절·응답 해석 실패는 생성 여부 확인 불가로 표시하고 자동 재전송하지 않는다. 단순 재시도 버튼으로 중복 생성하지 않는다. 현황 선도착만으로 현재 생성 요청 성공을 단정하지 않는다.

### 수신·응답·오류

- 받은 초대 → 응답 전송 중 → 전송 접수/서버 확정 확인 불가 또는 전송 실패를 구분한다. 로컬 수락/거절 선택과 서버 확정 상태를 별도로 둔다. 중복 입력과 반대 응답 전환을 막는다.
- 응답 자동 재발신은 하지 않는다. 같은 PENDING 초대를 재접속으로 다시 받으면 아직 응답 가능한 초대임을 반영하고 명시적 응답을 제공한다. 재접속 후 아무 메시지가 없으면 확정됐다고 가정하지 않는다.
- 확실히 귀속 가능한 INVITATION_NOT_FOUND는 해당 초대를 정리하지만 취소·시작·만료 중 무엇인지 단정하지 않는다. 응답 충돌은 이미 확정된 응답을 바꿀 수 없음을 안내하되 실제 결정 방향을 추정하지 않는다.
- 알 수 없는 타입·잘못된 JSON/필드·잘못된 ID·바이너리는 상태에 반영하지 않는다. 일반 메시지 ERROR는 안전한 한국어 문구로 안내하고 정상 연결을 끊지 않는다. 인증 만료·전송 장애는 기존 연결 정책을 따른다. JWT·개인정보를 로그에 남기지 않는다.

### 시작·취소·늦은 결과

- 시작과 취소 중 하나가 진행 중이면 둘 다 제한한다. 수락/거절·시작·취소 경쟁의 결과는 서버 처리 결과를 따른다. 409는 원인을 안내하고 404를 취소 성공으로 해석하지 않는다.
- REST와 알림 중 서버 확정 근거를 먼저 반영한다. 이후 늦은 실패·이전 현황으로 확정 상태를 되돌리지 않는다. 네트워크 오류만으로 시작·취소 완료를 표시하지 않고 무조건 재전송하지 않는다.
- rideSessionId별로 시작 REST/알림 중복 이동을 막는다. 역할이 확인되면 `rideSessionId`·`groupId`·`LEADER/MEMBER`를 임시 주행 목적지에 전달한다.
- 취소는 invitationId별 중복 정리를 막는다. 종료된 초대 ID와 처리한 주행 ID는 세션 안에서 유지해 늦은 초대·현황·REST 응답이 종료 상태를 복원하지 못하게 한다.
- 시작 알림에 invitationId가 없으므로 정확히 연결할 수 있는 문맥만 종료 처리한다. 모호한 다른 초대·다른 주행을 함께 정리하지 않는다. 서버 확정 순서와 일치하지 않는 메시지는 상태 복원 근거로 쓰지 않는다.

## 7. 검증 계획과 기존 결과 사용

- 문서만 바꾸는 0단계는 참조·내용·변경 범위만 확인한다. 빌드·lint·테스트·Preview·서버 요청·기기 실행을 하지 않는다.
- 구현 시 기존 JVM 테스트·로컬 HTTP 계약 도구·LoginSocket의 로컬 WebSocket 테스트 패턴을 재사용한다. 필요하면 기존 도구를 변경 범위만 확장하고 새 라이브러리는 추가하지 않는다.
- REST 계약: 생성/시작/취소의 경로·메서드·Bearer·성공 코드·필드 검증, 400/401/403/404/409/500, 잘못된 응답·응답 단절·HTTP 취소·자동 재전송 없음.
- 소켓: 초대/현황/시작/취소/ERROR 파싱, 엄격한 boolean 발신, 잘못된 메시지 무시, 정상 연결 유지·Ping/Pong·기존 인증 헤더. unknown 메시지를 무시하던 기존 테스트는 변경된 수신 경계에 맞춰 검증한다.
- 상태: 리더 ID 제외 집계와 canStart, 현황 선도착, 생성/응답 중복, 시작·취소·응답 경쟁, REST/소켓 중복과 늦은 결과, 종료 상태 복원 방지, 오류 귀속 불명확·동일 그룹 역할 모호성.
- 생명주기: 구성 변경·화면 이동 중 수신 유지, 백그라운드/연결 단절·재접속 복구 범위, 로그아웃·사용자 변경·이전 연결 이벤트 차단. 실제 Activity 재생성 조작과 상태 단위 테스트는 구분한다.
- 직접 관련 회귀는 인증 연결·메인 알림 중첩·그룹/멤버 왕복과 완료 상태 중심이다. 기존 과거 테스트 수치를 새 실행 결과로 쓰거나 모든 검증을 무조건 반복하지 않는다.
- UI는 기본 Preview 렌더링과 변경 범위 빌드·lint를 확인한다. 긴 그룹명/닉네임·집계·안내·좁은 창·확대 글꼴은 필요한 조건만 추가한다. 추가 Preview·캡처·에뮬레이터 설치를 기본 요구로 만들지 않는다.
- 실제 서버는 환경이 준비되어 실행 가능한 경우만 별도로 확인한다. 이전 멤버 선택 단계의 시간 초과는 과거 사실이며 현재 서버 상태로 단정하지 않는다. 서버 설정·DB·계정을 임의 변경하지 않는다.
- 실기기는 사용자가 나중에 직접 확인한다. 우선 가능한 휴대폰 한 대의 주요 흐름으로 시작하고 모델·Android 버전·실행 조건을 기록한다. 추가 기기는 문제나 최종 점검 필요에 따라 확인한다.
- Preview 정의·실제 렌더링·일반 JVM·로컬 HTTP/WebSocket·실제 Spring 서버·실기기 결과를 나눈다. 일반 JVM과 HTTP 계약이 같은 출력 XML을 갱신할 수 있으므로 명령·실행 범위를 구분한다.
- 기존 멤버 선택 1단계 Preview·2단계 JVM/빌드/lint·로컬 HTTP 27개는 해당 계획의 과거 기록이다. 이번 초대 기능의 검증 결과가 아니며 새 변경·실패·미해결 문제와 관련된 경우에만 다시 확인한다.

### 1단계 UI·화면 이동 완료 (2026-11-18)

- 승인 범위: 리더 현황·멤버 수신·응답 후 대기 UI, 접기/재열기·기존 팝업과의 표시 조정, 임시 주행 화면과 ID·역할 전달 경로. REST·WebSocket 수신/발신·서버 성공 처리·시작/취소는 구현하지 않았다.

### 2-A 공통 소켓·초대 생성·리더 현황 완료 (2026-11-18)

- 승인 범위: 공통 로그인 소켓 텍스트 수신·발신 기반, 초대 생성 REST, 성공 후 메인 이동·리더 현황과 재접속 최신성. 2-B·2-C는 활성화하지 않았다. 시작 시 1단계 변경은 사용자 측에서 반영된 상태로 작업 트리가 깨끗했다.
- `LoginMessageChannel`의 사용자·세션 세대·연결 세대 식별과 원문 텍스트 스트림을 추가했다. LoginSession의 기존 세대·foreground·만료 검사 이후에만 메시지를 제공하며 같은 연결로 발신한다. 발신 boolean은 서버 ACK가 아니다. 예전 연결 콜백·백그라운드/인증 종료 후 발신을 막는다. 바이너리는 무시하고 기존 Ping/Pong·재연결·JWT 정리 정책을 유지한다.
- AppContainer의 기존 Main scope를 공유하는 `InvitationRepositoryImpl`을 앱 생성 때 즉시 구독시킨다. 화면/ViewModel 생성 전에 온 현황도 Repository가 처리한다. 상태는 메모리이며 화면별 소켓·주기 폴링·새 라이브러리·DB 저장은 없다.
- `HttpInvitationApi`·도메인 모델·Repository를 추가했다. 기존 ServerEndpoint·OkHttp 설정과 AuthenticatedSession의 Bearer·401 정리를 재사용한다. 정확한 201·응답 ID·그룹 ID·대상 수·PENDING을 확인하며 예상 밖 응답은 생성 성공이 아니다. 취소 가능한 HTTP와 기존 자동 재전송 비활성 설정을 유지한다.
- 멤버 ViewModel의 `invitationSelection()`이 현재 사용자·연결·확인된 스냅샷과 유효한 선택을 검사해 그룹 ID·복사한 userId 집합을 전달한다. 정상 앱 Route는 개발 중 팝업 대신 실제 생성으로 연결한다. 기존 standalone/미연결 Route의 완료 팝업 fallback과 과거 테스트는 보존하며 실제 앱 경로와 구분한다.
- 생성 중 선택 변경·새로고침·완료 중복·상단/시스템 뒤로 가기를 제한하고 진행 안내를 표시한다. 201 후 생성 ID의 상태를 저장하고 메인으로 한 번 이동해 해당 ID의 팝업을 표시한다. 빠른 중복 클릭과 생성 성공 후 이동 전 중복, 이동한 뒤 남은 이전 화면 콜백도 차단한다. 구성 변경·재수집으로 POST를 재전송하지 않는다.
- 명확한 실패는 멤버 화면·선택을 유지한다. INVALID_INVITEE·USER_OFFLINE은 새로고침 후 재확인, 403·그룹 없음은 그룹 복귀를 안내하고 완료를 제한한다. 401은 기존 세션 종료를 따른다. 네트워크 단절·타임아웃·5xx·깨진/예상 밖 응답은 생성 결과 불명확으로 구분해 같은 로그인 세션에서 자동/단순 재전송을 막는다. 목록/재열기나 연결 복구가 이 제한을 임의 해제하지 않는다.
- 생성 REST보다 먼저 온 현황은 invitationId별 캐시에 보관하고 201의 같은 ID·선택 대상 집합과 합친다. 초기 PENDING으로 최신 현황을 덮지 않는다. 현황이 없으면 집계 null·확인 중으로 표시한다. 모르는 다른 ID나 같은 닉네임·대상 유사성으로 현재 POST의 성공을 추정하지 않는다.
- 현황 파서는 ID·중복·닉네임·상태·정수/boolean 자료형·acceptedCount/전체 목록/canStart 일관성을 검증하고 후행 쓰레기 데이터·잘못된/알 수 없는 메시지를 무시한다. 현재 인증 사용자 ID가 ACCEPTED 리더인지 확인하고 알려진 초대는 대상 집합도 확인한다. UI는 그 ID만 제외해 요청/수락/대기/거절을 계산한다. canStart는 서버 값을 전달하되 시작 기능은 아직 비활성이다.

## 9. 사용자 확인 절차

### 준비와 기록

- README의 현재 서버 주소·연결 방식으로 REST와 로그인 WebSocket이 모두 연결되는지 확인한다. 주소가 바뀌면 기존 `ridesyncBaseUrl` 한 곳을 수정해 다시 빌드하고, 휴대폰 loopback 사용 시 해당 기기의 adb reverse를 설정한다. 이 단계에서는 주소/연결 설정을 변경하지 않았다.
- 기존 테스트 계정으로 리더 1명과 해당 그룹의 APPROVED 멤버 1명을 준비하고 두 계정 모두 포그라운드에서 로그인 소켓을 연결한다. 초대 양측 확인에는 최소 두 인증 세션이 필요하다. 주 확인 휴대폰 한 대와 상대 계정의 별도 실행 환경으로 시작하며, 처음부터 S26+·S10 5G와 모든 팀원 기기의 전체 조합을 반복하지 않는다.
- 단순 흐름은 유효 초대 하나로 시작한다. 독립 시나리오 사이에는 확인 가능한 기존 초대를 리더의 취소 버튼으로 정리한다. 같은 그룹의 종료 문맥을 제거해 독립적인 시작 흐름을 확인하려면 양측 재로그인 후 새 초대를 사용한다. 결과 불명확을 없애려고 초대를 반복 생성하거나 재로그인을 서버 취소/주행 종료로 취급하지 않는다.
- 실행한 날짜·기기 모델/Android 버전·서버 연결 방식·리더/멤버 역할·절차와 실제 결과만 기록한다. 화면/글꼴/키보드 조건은 문제와 관련될 때 추가하고 비밀번호·JWT·개인정보는 기록/캡처에 넣지 않는다. 현재 APK는 `app/build/outputs/apk/debug/app-debug.apk`이며 설치/실행 검증 완료를 뜻하지 않는다.

### 주요 흐름과 기대 결과

| 순서/시나리오 | 조작과 기대 결과 |
|---|---|
| 1. 생성·리더 집계 | 리더가 그룹·온라인 멤버를 선택해 완료한다. 생성 중 완료/선택/새로고침/뒤로 가기가 제한되고, 201 확인 후 메인에서 실제 현황이 보인다. 요청 1·수락 0·대기 1로 리더 본인을 제외하며 시작은 비활성이다. 현황이 늦으면 임의 숫자 대신 확인 중을 표시한다. |
| 2. 수신·접기·재열기 | 멤버의 현재 인증 화면 위에 그룹/리더 정보가 있는 팝업이 나타난다. 바깥 터치는 무시하고 뒤로/나중에 보기는 응답 없이 접는다. 메인의 라이딩 초대·대기로 다시 연다. 기존 알림/그룹 팝업이 열려 있으면 중첩하지 않고 그 팝업을 닫은 뒤 표시한다. |
| 3. 거절·취소 | 멤버가 거절을 한 번 누르면 거절 응답 전송됨과 확정 확인 불가가 표시된다. 멤버 앱에서 확정 성공으로 표시하지 않으며, 리더의 실제 갱신된 거절 집계를 별도로 확인한다. 리더가 취소하면 해당 현황이 정리되고 멤버는 취소 안내 후 기존 화면을 유지한다. 수락 후 대기 상태에서도 취소 정리를 별도 확인할 수 있다. |
| 4. 수락·시작 | 독립된 새 초대에서 멤버가 수락한다. 전송됨/시작 알림 대기와 확정 확인 불가를 확인하고 리더의 실제 수락 집계·canStart 갱신을 기다린다. 리더가 시작하면 진행 중 시작/취소가 제한되고, 서버 확정과 명확한 문맥에서 각각 선두 주행 화면·후미 그룹 주행 화면 텍스트만 보인다. 미응답/거절 멤버가 주행으로 이동하면 실패다. |
| 5. 주행에서 메인 왕복 | 양측에서 시스템 뒤로 가기로 메인에 복귀하고 주행 화면 다시 열기로 같은 역할 화면을 연다. 뒤로 가기는 종료가 아니다. 같은 주행 알림/현황 갱신으로 메인에서 주행이 저절로 다시 열리면 실패다. 이 앱에는 실제 주행 종료 기능이 없다. |
| 6. 연결 단절·복귀 | 시작 전 초대에서 한쪽의 네트워크/포그라운드 상태를 바꾼다. 단절 자체가 거절·취소가 되지 않고 변경 동작이 제한되는지 확인한다. 리더 집계는 새 현황 전까지 이전 값임을 표시한다. 멤버는 실제 PENDING 초대 재수신 시에만 응답 가능 상태를 갱신하며, 이전 선택이 있으면 같은 선택만 직접 재전송한다. 알림 미수신은 확정 성공/만료가 아니다. |
| 7. 오류·세션 정리 | 가능하면 별도 재현 환경에서 생성/시작/취소의 응답 단절·권한/404·ERROR를 확인한다. 불명확 결과·취소 404는 성공 처리/단순 재요청하지 않아야 한다. 로그아웃·다른 사용자 로그인 후 이전 초대/주행/늦은 콜백이 나타나면 실패다. 재현하지 않은 오류를 실기기 통과로 기록하지 않는다. |

복수 초대·같은 그룹 종료 이력 때문에 시작 이동이 보류되면 초대/역할을 추정해 화면을 강제로 여는 대신 그 상태와 선행 조작을 기록한다. 이는 현재 서버 계약 아래에서 명시한 보수적 처리 한계다. 실제 정상 단일 초대에서도 보류되거나 표시/조작 문제가 있으면 리더와 멤버 양측의 연결 상태·현재 화면·재현 순서를 함께 남겨 후속 수정 범위를 정한다.
